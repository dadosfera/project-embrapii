# Design System: PAIRS

> Visual identity, componentization and UI patterns.
> Implementation: `frontend/src/index.css` (tokens) and `frontend/src/components/ui/`
> (primitives). Application architecture: `docs/architecture.md`.
>
> This document is written in English; user-facing strings quoted from the product
> stay in Portuguese, which is the interface language.

## 1. Overview

**Creative North Star: "The Quiet Validation Desk"**

PAIRS is a contained operational surface, built to sustain focus while a technical person works through a queue of queries. The system does not dramatize the work: stone and charcoal neutrals structure the screen, thin-bordered panels organize context, and petrol blue appears only where there is a primary action or real progress.

State must be understood before ornament. Approval, rejection, pending review and local edits combine text, symbol and semantic color; motion only accompanies a true change, such as progress advancing, a notification arriving, or the transition to the next item.

The product has two surfaces with distinct registers, on top of the same token base:

- **The application** (5-step wizard, review, agent configuration) — dense, quiet, built for repeated work.
- **The landing page** — narrative, using the pipeline's indigo → cyan gradient as its leitmotif, with scroll reveals. It is the only place where the brand speaks louder than the content.

**Key Characteristics:**

- Neutral, compact, low-saturation surfaces.
- Clear operational hierarchy: pipeline, queue, editor, validation, advance.
- Petrol blue kept rare and functional; green, red and amber reserved for state.
- Teal CTA for the continuity action; never for a verdict.
- Mono restricted to SQL, dialect, identifiers, counts and tabular data.
- Thin borders and 7–14px radii instead of decorative shadows.
- States legible through text and symbol, never through color alone.
- Light and dark themes with the same hierarchy, defined exactly once.

## 2. Themes and tokens

### 2.1 One definition per value

Every theme-dependent value is declared **once**, with `light-dark()`, in `:root` of `index.css`. There is no duplicated dark-mode block to keep in sync; `light-dark()` resolves against the computed `color-scheme`, and the `data-theme` attribute is the only switch.

```
:root                     → color-scheme: light dark   (follows the OS)
:root[data-theme="light"] → color-scheme: light
:root[data-theme="dark"]  → color-scheme: dark
```

The preference has three states — `system` (default), `light`, `dark` — persisted in `localStorage` under `pairs.theme` and applied **before React mounts** (`initTheme()`), so the first paint is already in the right theme, with no flash.

Tailwind's `dark:` variant was redefined (`@custom-variant dark`) to follow the same rule: the OS preference, unless an explicit `data-theme` overrides it. Without this, the toggle would flip the tokens and leave every `dark:` class behind.

**The Single Source of Theme Rule.** No color may have its only definition inside a `@media (prefers-color-scheme)` block or a stray `dark:` class. A new color enters as a token in `index.css`.

### 2.2 Token layers

1. **Brand** (`--color-brand-*`, `--color-cta`) — fixed identity hexes.
2. **Semantic** (`--bg`, `--panel`, `--text`, `--text-muted`, `--border`, `--subtle`, `--editor`, `--focus-ring`) — what components actually consume.
3. **Feedback** (`--success`, `--danger`, `--warning` and their `-soft` variants) — also exposed as Tailwind utilities (`text-danger`, `bg-warning-soft`).
4. **Pipeline** (`--step-1` … `--step-5`) — the five stage accents.

Components reference the semantic layer, not the brand layer: `bg-[var(--panel)]`, never `bg-white`.

### 2.3 Dark-theme contrast

The brand hexes were authored against a white page and collapse on a dark background — indigo dropped to 1.37:1 against `--bg`. The pipeline accents therefore **lift lightness and chroma in dark mode while holding the hue**; each of the five clears 4.5:1 against both `--bg` and `--panel` in both themes.

**The Painted-On Text Rule.** Text painted *on* a pipeline accent uses `var(--bg)`, never white: at dark-mode lightnesses, white falls to 1.9:1.

## 3. Colors

The palette balances warm stone and charcoal with a sober petrol blue; the more saturated colors carry semantic, continuity or progress meaning.

### Primary

- **Action Petrol Blue** (`--color-brand-blue`): primary action, visible focus and confirmed progress.
- **Origin Indigo** (`--color-brand-indigo`): the pipeline's start; participates only in the persistent progress gradient.
- **Destination Cyan** (`--color-brand-cyan`): closes the pipeline gradient; never competes with actions or states.
- **Continuity Teal** (`--color-cta`): the action that moves the flow forward — generate, continue, finish. The only accent that appears on the landing page as an invitation.

### Neutral

- **Content Charcoal** (`--text`): primary text.
- **Background Stone** (`--bg`): low-saturation global canvas.
- **Panel White** (`--panel`): work areas, cards and surfaces elevated by tonal contrast.
- **Support Gray** (`--text-muted`): metadata, help, counts and secondary text.
- **Stone Border** (`--border`): separators, field outlines and panel edges.
- **Subtle Stone** (`--subtle`): quiet hover, tracks, table headers and editor line numbers.
- **Editor Stone** (`--editor`): background for editable fields, switching to the panel color on focus.

### Tertiary

- **Approval Green** (`--success`): the approved verdict, and only that verdict.
- **Correction Red** (`--danger`): rejection, failure cause and destructive discard.
- **Change Amber** (`--warning`): a modified draft that still needs revalidation.

### Named Rules

**The One Functional Accent Rule.** Petrol blue is restricted to primary action, focus and progress; it never colors whole surfaces.

**The Semantic Exclusivity Rule.** Green, red and amber are never decoration: they mean approved, rejected, or changed-and-pending-validation.

**The Quiet Canvas Rule.** Saturated blue backgrounds are forbidden; the canvas stays stone/charcoal so content and state take precedence.

**The Continuity vs. Verdict Rule.** Teal moves the flow forward; green judges an item. Swapping them makes the user read advancement as approval.

## 4. Typography

**Display:** Space Grotesk · **Body:** Inter · **Mono:** JetBrains Mono
All self-hosted through `@fontsource` (weights 400/500/600 as needed), with no CDN request.

**Character:** Space Grotesk gives headings technical precision without a terminal look. Inter keeps reading compact and neutral; JetBrains Mono creates alignment only where the structure of the data matters.

### Hierarchy

- **Headline** (semibold, 24px): page title and major milestones.
- **Title** (semibold, 18px): product mark and higher-emphasis group headings.
- **Body** (regular/medium/semibold, 14px): instructions, labels, buttons and operational content.
- **Label** (medium, 12px): metadata, help, counts and state badges.
- **Data** (regular/medium, 11–14px): SQL, dialect, run identifiers, dataset names and preview tables.

`h1`–`h3` globally receive the display font, weight 600 and `letter-spacing: -0.01em`; components need not repeat that.

### Named Rules

**The Mono Has Meaning Rule.** Use JetBrains Mono only when alignment, syntax or technical identity adds information; never in navigation or ordinary prose. Run id, dataset and progress captions are mono because they are identifiers; titles and buttons are not.

## 5. Layout

### 5.1 Application shell

`AppShell` mounts a sticky header with three zones — brand, **pipeline rail**, and session controls (theme, sign out) — over `--panel` at 85% with `backdrop-blur`. Content is centered at `max-width: 1440px`, with 16px of side padding on mobile and 32px from desktop up.

On mobile the header becomes a two-row grid: brand and controls on the first, the rail spanning full width on the second. The dataset identifier moves below the brand, in 11px mono.

### 5.2 Step footer

Every wizard step ends in `StepFooter`: a **fixed** (not merely sticky) bottom bar, with back on the left and the primary action on the right. Fixed so it stays reachable no matter how long the page above it is; capped at `45dvh` with internal scrolling so it never swallows short viewports. On mobile the buttons stretch to fill their column; from `sm` up they return to their natural size.

Main content reserves 112–144px of `padding-bottom` so it never sits under that bar.

### 5.3 Review

In SQL review, the first desktop viewport shows progress, a 300px queue and the editor at once. The queue is sticky and scrolls vertically; the main panel takes the remaining space. Rhythm uses 4, 8, 12, 16 and 20px increments, with 24px separating larger blocks.

Below 1024px, queue and editor stack; the queue becomes a horizontal strip of 280px cards. Below 640px, headers and action groups switch to a column, keeping controls free of horizontal overflow.

**The Editor-First Mobile Rule.** Pipeline and queue compact horizontally on mobile so the editor appears early in the scroll.

## 6. Elevation & Depth

The system is flat by default. Depth comes from tonal contrast, 1px borders and positioning. Shadow appears only when something must separate from the content plane: the translucent blurred header and footer, modal dialogs, and the hover state of clickable cards.

### Shadow Vocabulary

- **Inner selection** (`inset 0 0 0 1px var(--border)`): the current queue item.
- **Interactive card hover** (`0 2px 10px rgb(0 0 0 / 0.06)`): only on `Card interactive`.
- **Filled button** (`0 1px 2px rgb(0 0 0 / 0.16)`): gives the CTA an optical edge on light panels.
- **Active-stage halo** (`0 0 0 4px color-mix(...)`): marks the current pipeline stage only.

### Named Rules

**The Flat-by-Default Rule.** Panels stay flat; shadows appear only when selection, overlay or state require separation.

## 7. Shapes

A single radius scale, defined as tokens, replaced the arbitrary values (`rounded-[7px]` … `rounded-[14px]`) that components used to pick on their own:

| Token | Value | Use |
|---|---|---|
| `--radius-xs` | 7px | Compact rail targets |
| `--radius-sm` | 8px | Fields, editor, queue items |
| `--radius-md` | 10px | Buttons |
| `--radius-lg` | 12px | Inner panels, dialogs |
| `--radius-xl` | 14px | Cards and page containers |
| pill | 9999px | Badges, dots, progress bars |

**The Compact Radius Rule.** Up to 10px for interaction, 12–14px for containers; radius should organize the interface, not infantilize it.

## 8. Componentization

### 8.1 Principle

`components/ui/` holds primitives with no domain knowledge; `components/` holds the components that know what a SQL query, a job or a stage is; `pages/` composes both. A primitive is created once the same design has been hand-written in more than one place and started to drift — that is how `Card` was born, after the same panel appeared on every page with radii between 12 and 14px.

**The Token-Only Component Rule.** A primitive takes no literal color: it exposes named variants (`tone`, `variant`) that map to tokens. An arbitrary color passed in from outside reintroduces the drift the primitive was created to fix.

### 8.2 Primitive catalog (`components/ui/`)

| Component | Role | Variation |
|---|---|---|
| `Button` | Every clickable action | `variant`: cta · primary · secondary · ghost · danger · danger-solid; `size`: sm/md/lg; `loading`, `iconOnly` |
| `Card` + `CardHeader/Body/Footer` | Content panel | `padding`: none/sm/md/lg; `interactive` |
| `Badge` | State or metadata label | `tone`: neutral · success · warning · danger · info |
| `Input`, `Textarea`, `Select`, `Field`, `FileField` | Data entry | `ControlSize`; `Field` supplies label, help and error |
| `Combobox` | Searchable selection | typed options |
| `TagInput` | List of short values | — |
| `NumberStepper`, `Slider` | Quantities (query count, paraphrase count) | — |
| `Checkbox`, `Switch` | Booleans | — |
| `Dialog`, `ConfirmDialog`, `useConfirm` | Modal overlay and destructive confirmation | — |
| `Disclosure` | Expand/collapse | animates `grid-template-rows` 0fr↔1fr |
| `ErrorMessage` | Inline failure | — |
| `Skeleton` | Waiting for data | `lines` |
| `ListItem` | Uniform list row | — |

### 8.3 Domain components (`components/`)

`PipelineRail` (the five stages and job progress), `SqlEditor`, `PreviewTable`, `StatusBadge`, `JobStatus`/`JobFailure`, `DifficultyPicker`, `StepFooter`, `Toast`/`ToastViewport`, `RestartPipelineDialog`, `Reveal`.

### 8.4 Buttons

- **CTA** (teal): the action that advances the flow — "Gerar", "Continuar", "Concluir".
- **Primary** (petrol blue): the main action *within* a step, such as "Validar e aprovar".
- **Secondary**: panel background, stone border, tonal hover.
- **Ghost**: text/icon only, for header controls and tertiary actions.
- **Danger**: neutral text that reveals red on hover; requires explicit confirmation.
- **Danger-solid**: reserved for the final confirmation inside a destructive dialog.

Only the filled variants lift on hover — a ghost button growing under the cursor reads as a glitch, since it has no edge to anchor the movement. `loading` swaps the content for a spinner **without collapsing the width**, so the action bar does not jump.

### 8.5 Badges and state

`Badge` covers generic labels; `StatusBadge` translates the API's `CurationStatus` with icon + text:

| State | Icon | Text | Color |
|---|---|---|---|
| approved | `CheckCircle2` | "Aprovado" | green |
| rejected | `XCircle` | "Rejeitado" | red |
| pending | `CircleDashed` | "Aguardando revisão" | neutral |
| locally edited | `RotateCcw` | "Alterado" | amber |

**The Verdict Is Literal Rule.** A badge shows approval only after the database's verdict; editing a query visually replaces the previous state with the needs-revalidation state.

### 8.6 Inputs / Fields

Thin border, `--editor` background, 8px radius. On focus the background switches to `--panel` and takes a 2px petrol-blue outline. Hover brings the border closer to the secondary text color without changing geometry. The rejection reason sits in a discreet red strip; disabled controls lower opacity and never blink.

### 8.7 Pipeline rail

The rail is the system's most expressive component and carries three pieces of information at once: where the user is, how far they may navigate, and what is currently running.

- Five connected dots, each with its accent (`--step-1` … `--step-5`); future stages use neutrals and opacity.
- The current page's stage expands its label; the others collapse to the dot.
- While a job is active, **its stage takes over the rail's flexible middle**: labels retract, neighbors settle toward the edges, and the connector becomes a progress bar. The same DOM stays mounted, so the movement reads as continuity rather than a screen swap.
- Known progress fills the bar; indeterminate progress uses a continuous sweep. The active dot breathes in a 2.8s halo; completion confirms with an icon that opens as a circle.
- The phase caption is mono, 11px, and turns green or red at the outcome.

**The Progress Interpolation Rule.** Polling arrives every 1.5s; the fill interpolates over 1.1s so the advance reads as continuous rather than as a staircase.

### 8.8 SQL Editor

JetBrains Mono, an initial height of 14 lines and vertical resize, with no side bar eating into the usable area. `Tab` indents and `⌘/Ctrl + Enter` runs "Validar e aprovar". The preview is a temporary test, kept separate from the verdict, shown below the editor as a scrollable table.

### 8.9 Feedback: toast, failure and skeleton

- **Toast** is transient and meant for confirmations: 6s for routine, 9s for errors, dismissible by button, sideways drag or two-finger swipe. Module-level store, no provider.
- **`JobFailure`** is persistent: a failed generation keeps the server's explanation on screen, with "Tentar novamente", until it is dealt with. A toast would carry the reason away within seconds and leave the user facing a re-enabled button with no idea why.
- **`Skeleton`** replaces "Carregando…" while preserving the content's approximate size, so the page does not jump when data lands. It sweeps a highlight — which reads as "loading" — instead of pulsing opacity, which reads as "disabled"; under `prefers-reduced-motion` the animation does not run.

**The Persistent Failure Rule.** An error that requires a decision stays on screen; only confirmations disappear on their own.

## 9. Landing page

Editorial register, same token base. The pipeline's indigo → cyan gradient is the leitmotif: a hero with an artifact card that cross-fades its content, an indicator that fills over the rotation interval (and pauses on hover), scrollytelling of the five stages, and anchors with `scroll-margin-top` so headings do not land behind the sticky nav.

Scroll reveals use `transition` — not `animation` — triggered by an `IntersectionObserver`, with a per-item stagger delay. Under `prefers-reduced-motion`, `.reveal` **opts out entirely** and renders as plain content: the global rules only collapse durations, and an element whose resting state is invisible would stay invisible forever if its observer never fired.

## 10. Motion

| Movement | Duration | Curve |
|---|---|---|
| Color, border, background | 120–160ms | ease |
| Expand/collapse (`Disclosure`) | 260–300ms | ease-out-expo |
| Progress fill | 1100ms | cubic-bezier(0.2, 0.75, 0.25, 1) |
| Rail: labels, connectors, flex | 600–720ms | ease-spring |
| Landing reveal | 520ms | ease-out-expo |
| Toast/tray entrance | 200ms | ease-out |

`--ease-spring` is a critically damped spring with no overshoot: the first version covered 38% of its distance in 46ms and made the rail feel like it snapped open.

`prefers-reduced-motion` reduces animations and transitions to near-instant, disables `scroll-behavior: smooth` and neutralizes the reveals.

**The Motion Follows Truth Rule.** Motion accompanies a real state change — progress, an arriving notification, advancing to the next item. There are no decorative loops; the job halo and the indeterminate sweep are the justified exception, because they represent work in flight.

## 11. Accessibility

- Global visible focus: a 2px outline in `--focus-ring` with 2px offset; never removed without a replacement.
- Every state combines **text + icon + color**; no meaning depends on color alone.
- Icon-only buttons require `aria-label`; `Skeleton` announces itself with `role="status"`; job failure uses `role="alert"`.
- Rail touch targets grow to 40×40px on coarse pointers (`@media (pointer: coarse)`).
- Minimum contrast of 4.5:1 verified in both themes, including the five pipeline accents.
- Scrolling: a thin themed scrollbar that darkens on hover, instead of the browser default.
- Review shortcuts (`⌘/Ctrl + Enter`) are complementary — every action remains reachable by click and by tabbing.

## 12. Do's and Don'ts

### Do:

- **Do** keep the canvas stone/charcoal and use tonal contrast to structure the screen.
- **Do** consume semantic tokens (`var(--panel)`, `var(--text-muted)`), never literal colors.
- **Do** define any theme-dependent value exactly once, with `light-dark()`.
- **Do** use `Button`, `Card`, `Badge` and `Field` instead of rebuilding the design by hand.
- **Do** treat "Validar e aprovar" as the primary action and advance automatically after approval.
- **Do** reserve teal for continuity and green for verdicts.
- **Do** combine text, symbol and color in every review state.
- **Do** keep the rejection or failure reason on screen until it is dealt with.
- **Do** keep "Validar todas" a secondary action.
- **Do** use short motion only for real state changes, and respect reduced motion.
- **Do** keep SQL, identifiers and data in mono, with prose and navigation in Inter.

### Don't:

- **Don't** use saturated blue backgrounds or gradients as large application surfaces.
- **Don't** write `bg-white`, `text-gray-500` or a loose hex inside a component.
- **Don't** create a separate dark-mode block, or a color defined only inside `dark:`.
- **Don't** paint white text on the pipeline accents in dark mode.
- **Don't** show approval before the database's actual response.
- **Don't** force the user to save separately before validating.
- **Don't** use ambiguous badges — color-only, or without a recovery verb.
- **Don't** let a failure disappear on its own inside a toast.
- **Don't** add blinking, pulsing or looping animation that is merely decorative.
- **Don't** let batch validation compete visually with item-by-item review.
- **Don't** apply mono to titles, buttons or explanatory text.
